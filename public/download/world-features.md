# Maps, people, barter and session time

These features use the same campaign, room permissions, location hierarchy, purses, inventory, property deeds and campaign clock as Market and Property Management. Existing saves remain readable. Shared raster images are deduplicated in campaign-private D1 rows by additive migration `0012_campaign_room_images.sql`, outside the single room JSON row; no public image endpoint is added. Room writes and image inserts share the same atomic revision-checked batch. Device/shared exports hydrate full original raster data, including archived snapshots; referenced images remain available after room closure. Existing cloud recovery-size limits still refuse an oversized complete copy before deleting a room, so download a complete device export when needed. The sixth main tab is **Maps**; all five earlier tabs remain.

## Maps

DMs import PNG, JPEG or WebP maps, name them and optionally select their existing region, city/town or area. Import multiple maps for world, regional and local views; a map matching the party's closest current-location ancestor opens by default. Original uploads can be up to 20 MB / 64 megapixels; the shared raster is compressed to at most 2400 pixels on the long edge and 500,000 data-URL characters. If a map cannot fit, split it into regional maps. No SVG scripts or external image URLs are accepted. Keep original files for future re-import.

Choose **Read location labels** to run the already-bundled English OCR on the device. It matches whole, unambiguous existing location names and suggests normalized positions. Review the image and anchors before saving. Duplicate names, stylized labels, non-English text and unreadable scans need manual anchors: **Link location**, tap the image, choose the existing location, then save. The tool does not invent places, claim geometric accuracy or move the party during import. Replacing the image clears its old anchors. Anchors can be removed in Edit map and repositioned through Link location.

The party marker follows Market's selected party location. If an area has no anchor, its nearest anchored ancestor supplies the position. If no ancestor is anchored, the screen says the party is unplaced. **Move party here** uses the same DM location command as Market. Properties, shops, permitted nearby NPCs and designated post offices are attached to location anchors and listed in the map register; grouped map badges avoid stacking labels. Player maps include only their owned/accessible property records and visible vendors/NPCs. A shipment stays associated with its existing property's records; this is not a simulated moving route.

**Place marker** adds a named point and description live. A marker can be shared or DM-only; Remove marker removes it in the shared room. Maps themselves may be DM-only. Image pixels cannot be redacted by hiding a marker: players see everything drawn in an image that the DM shares. Secret marker text is omitted from player responses, archives and public change notices.

Drag with a mouse or finger to pan. Scroll-wheel and two-finger pinch zoom around their focus; +/− buttons, arrow keys and Home provide alternatives. Fit map restores its fitted view. Coordinates are relative to the image and remain stable when its viewport changes. Viewport zoom/pan is local to each reader, while the image, anchors and markers use authoritative room commands. Turn-based changes follow the existing turn queue; Live changes arrive on the existing room sync.

## Non-party NPCs

Open **Market → People & NPCs**. DMs create/import location NPCs with name, description, portrait, starting funds and canonical inventory. They remain outside party counts, player character selection and party wealth. Presence requires a known selected party location in the NPC's city/region/area path. Hiding or moving an NPC removes it from ordinary player responses. Archive an NPC by clearing visibility; its inventory, funds and history are retained.

The DM configures stock and funds and speaks for the NPC by default. Optionally assign an existing player character as controller: that character's authorized player may respond as the NPC and decide NPC trades. This delegates dialogue and consent, not configuration or unrestricted wallet access. Conversation threads are between a party character and that NPC and are visible only to that character's player, the DM and the NPC's configured controller. Players see available NPC inventory, not the NPC's coin balance or character sheet. NPC replies are human-controlled; no automated dialogue service is added.

Import **strict UTF-8 JSON** with `format: "lootsplit.npcs"`, `schemaVersion: 1`, and a nonempty `npcs` array (up to 100 records per import, 500 total). Each record requires `name`, `description`, `locationId` and optionally `visible` (true), `barterAllowed` (false), `controllerPurseId` (null), `portrait`, `copper` (0), and `inventory` ([]). Each inventory entry requires `name`, positive integer `quantity`, nonnegative integer `unitCopper`, `notes`; `category` and compressed raster `image` are optional. All prices are whole copper. Location/controller IDs must already exist in this campaign. NPC and item IDs are generated, and imports create new records; they never overwrite existing NPCs or move the party. Review the preview before committing; a changed campaign requires another review. An invalid record rejects the entire import. The downloadable sample uses fictional names/values and placeholder location IDs that must be replaced. The JSON Schema validates structure; the authoritative command also validates references, limits and permissions.

## Trading and barter

Open **Market → Trading & Barter**. Offer any carried canonical item lots, goods, property deeds or coins to another party player or a nearby NPC configured with **Bartering allowed**. Party NPCs retain their earlier role; location-NPC bartering is separately configured. An offer may ask for coins or visible NPC goods. Another player's private inventory is not displayed: that player adds their goods in a counteroffer. Counteroffers reverse the recipient; only the current recipient can accept or decline, and a participant may cancel. The DM can act for either side, including NPCs.

Each acceptance rechecks participants, NPC presence/bartering permission, exact lot contents/quantity, custody, property obligations and each side's gross coin contribution. One atomic command exchanges both sides; retries use existing room content receipts and cannot repeat an exchange. No goods are reserved by merely proposing an offer. Spending, moving or editing an offered lot makes the old offer stale and requires a fresh offer. All participants can review pending offers and retained decision history; unrelated players cannot see them. Existing Give remains available.

Services, stored/in-transit/reserved lots and properties with active contents, projects, staff, tenants, financial agreements, orders or arrears cannot be bartered until resolved. Use Property Management's explicit DM handover when obligations must accompany an ownership change. A clean deed transfer updates its owner/image information, retains the original purchase receipt and removes the old owner's transferred lot. No second deed inventory asset or duplicate wealth is created.

## Black market

DMs use the Market **Black market** toggle during play to reveal or hide designated vendors. In a shop, open **Black-market vendor rules**, enable the flag and set a premium greater than 1 (default 1.5). Configure names, goods, quantities, rarities, illegal-goods descriptions, locations and schedules through the normal shop/stock tools. The premium multiplies the ordinary asking price before its existing Charisma adjustment. Finite/unlimited stock and ordinary receipts remain unchanged.

Hidden vendors/stock are absent from player projections. The server and local transaction paths recheck visibility, current location and closure at purchase/sale time, including stale queued actions. Property supplier orders also honor hidden-vendor availability and premiums while retaining their existing authorized remote delivery rules. The DM still sees and edits hidden vendors. Toggling does not open a closed shop or move the party. No fixed illegal-item catalog or real-world rules are imposed.

## Session time

DMs open **Session Time** from Market or Desk's session tools during an active recorded play session. Advance an integer 1–24 hours per action; repeat for longer journeys. Review the new clock, finance/stock changes and property work before approving. The same finance clock stores an optional minute-of-day remainder; old saves start at midnight. Crossing a campaign day settles existing recurring finances, shop schedules, postal/delivery/manager orders once. Partial-day advances do not repeatedly collect rents or arrears. Existing between-session downtime remains available; approve/cancel its pending quote before advancing time.

Optionally award no rest, a short rest or a long rest to selected party characters. The DM decides whether the time qualifies under the table's rules. Short rest restores configured short-rest resources. Long rest restores HP, death saves, spell slots and short/long-rest resources. Manual resources, hit dice, conditions, temporary HP and custom rules retain the existing sheet-button behavior. Rest changes increment sheet revisions and preserve coins, inventory and other sheet fields.

**Allow assigned characters to perform approved property downtime work** uses existing approved jobs, assignments, skills/checks, materials and presence permissions. Work is prorated over the existing 24-hour campaign-day unit; integer remainder tracking prevents repeated small advances losing labor. Hired contractors progress with elapsed time and the same budgets, material reservations and supervision rules. Without character downtime, travel/rest grants no character labor. Project stage completion retains the existing one-stage-per-settlement behavior; excess labor is not automatically carried into an unreviewed next stage. This is campaign time, with no wall-clock scheduler. All advances are DM-only, reviewed against a fresh economic state, journaled and retry-safe.
