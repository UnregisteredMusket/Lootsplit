# Owner monitoring, development status and widgets

Lootsplit's owner dashboard, bundled Android account screen, main Field monitor and independent 4×1 companion read the same private backend. Campaign DM, player, moderator and administrator roles do not grant owner monitoring access. Existing server monitoring, owner controls, gameplay, saves and permissions remain available.

## Permanent log and development rules

**Every future log explicitly requested or designated for Lootsplit must automatically become part of the daily report.**

Register each log before its first entry. In-code producers add a definition to `BUILTIN_LOGS` in `cloudflare/monitor-journal.mjs`, emit through its journal interface, and test both inclusion and missing-source coverage. No producer may maintain a separate invisible report history. Logs introduced outside this repository use **My account → Field monitor → Log registry & settings → Register an external or future log**, followed by **Record an external log entry or coverage check** or the authenticated API below. A registration is not proof that a source supplied data. Missing registered sources remain explicit coverage gaps. Original logs remain authoritative evidence; this registry cross-references them.

**Retiring a custom log (audit M10).** The owner can stop tracking a custom (non-built-in) registry entry without deleting it: expand it under **Log registry & settings** and choose **Retire**, then confirm; **Reinstate** resumes it. API: `POST registry/retire` and `POST registry/reinstate` with `{ id, revision, eventId, reason? }`; `revision` is the entry's current `revision` from `GET registry` (stale → 409) and `eventId` is a persistent idempotency key (a retry is applied once; reusing it for the other action → 409). Both routes use the owner session and the same in-transaction owner commit guard as other registry writes. Rules:

- No schema change: the current state (`retired: { retiredAt, retiredBy: { id, name }, reason }`), closed spans (`retirements: [...]`, each adding `reinstatedAt`/`reinstatedBy`) and `revision` live in the registry row's existing JSON `body`. Re-registering an existing ID keeps them and bumps `revision`; it never silently reinstates.
- Nothing is deleted. Every stored entry stays in history and export, entries may still be recorded for a retired log (late evidence is never refused), and each retire/reinstate is itself a history entry of that log (`registry:<log>:<eventId>`, `registryChange` in its body). Those audit entries are not counted as source data for coverage.
- Daily reports subtract retired spans from the time a source is expected to report. A log retired for the whole day is left out of `coverage` and listed in `retiredLogs` (with retiredAt, who, reason and any reinstatement); a log retired for part of the day stays in `coverage` with `retiredSpans`, and gaps are computed only over its active time. Retired time is never a missing-data gap; active time without data still is.
- Built-in logs (`BUILTIN_LOGS`) cannot be retired (409).
- Retired entries still count toward `REGISTRY_CUSTOM_LIMIT` (50). They keep their definition, history and report notes, so the cap stays a simple bound on registry size, and reinstating can never fail on a full registry.

Every development session publishes an explicit task start, meaningful progress, phase changes, expected long operations, pauses, blockers, handoffs and completion. Use the owner task form or `scripts/development-status.mjs`. Never infer activity from an open chat, old commit, queued PR or somebody's presumed availability. A handoff continues the existing task ID and revision. A new update receives a new ID. Store real evidence links and a useful next action. If publishing is unavailable, state the telemetry gap and publish the actual current state when restored; do not invent past heartbeats.

## Collection and reports

Migration `0016_owner_monitoring.sql` adds only private operational tables. Cloudflare's minute Cron dispatcher claims each UTC half-hour slot with a database lease; measurement collection runs once per slot, independently of phones, browsers and app processes. Entries retain scheduled time, actual collection time, outcome, attempt history, source freshness, measurement window, previous/current values, absolute changes and meaningful percentages. Retries use persistent IDs; a failed slot retries with backoff (1, 2, 4 … 32 minutes, at most six attempts) so a provider outage cannot multiply provider calls every minute. Failures and missed slots remain in history even after recovery. Expected intervals in a report count only slots after monitoring was installed; an unmonitored part of the first day is stated as a gap, not counted as missed. The interval whose window ends at local midnight belongs to the day it measured.

Instantaneous counts, rolling 5-minute/24-hour observations, cumulative current-campaign counters and exact preceding half-hour traffic totals are distinct. Missing readings are null/unavailable. Zero baselines have no percentage; decreased cumulative counters identify a reset/restoration/deletion rather than a negative rate. Changes compare the preceding available observation and retain its scheduled time. Counter totals can decrease when current campaigns change; they are not lifetime business totals. GitHub and 24-hour provider reads may be cached five minutes. Adaptive provider metrics retain the provider's scope; they are not an exact count of people online.

The dispatcher records older missed slots in bounded batches and attempts historical traffic recovery separately. Recovery never reconstructs unobserved storage, authentication, device or development state. A conservative 89-day historical traffic horizon avoids treating data beyond the provider's documented three-month retention as zero. Unrecoverable intervals remain gaps. Current collection continues after the backlog drains. An expired lease can be retried; an interrupted older observation becomes explicitly missed. Cron execution failure remains visible in Cloudflare; collection/report failures also receive sanitized journal entries when D1 is available. No database outage can be logged into that same database until storage recovers: inspect Cloudflare execution evidence and resulting missing slots.

Daily reports default to **00:10 America/New_York**, for the preceding calendar day. The owner can change the IANA timezone, local report time and warning thresholds in the dashboard. DST days retain their real 23/25-hour coverage. Half-hour traffic windows ending after the day's start and through its end belong to that report. Reports include every registered source, trends, incidents/recoveries, build/test/audit/deployment metadata, task states as of day end, performance history, evidence, missing coverage and recommended actions. Nearby events are described as correlation, never proof of cause. Late entries queue regeneration of already-created affected reports. Missed reports catch up one day per dispatcher invocation. A failed regeneration retains the previous report, but the daily-report component stays red until the same calendar report succeeds. Recovered traffic is displayed separately from the original unavailable measurement, with its actual recovery time and comparison window.

Existing performance capture remains on the `performance-history` branch. Its regressions, verified resolutions and capture cursor feed the daily report. **Inclusive ≥15% comparable slowdowns must still be investigated and documented under `docs/PERFORMANCE.md`.** Compare equivalent workloads and environments. Faster runs alone never reset a trend; retain the original history and use `performance:resolve` only after a diagnosed fix and successful comparable verification. Monitoring does not change these rules or label unavailable capture as healthy.

The storage/assets checks are real observations, and so is Multiplayer since the synthetic round-trip probe (below, 2026-10-22): it is a required check like the others. The coverage-limit mechanism (`required: false`, `coverageLimit: true`, named in `overall.notes`, `All required checks passed. Coverage limit noted (not a failure): <name>.`, widget row `<name> · coverage limit`) remains available for future by-design gaps; no current component uses it. A failed candidate workflow does not mean the deployed app failed. Workflow failures remain associated with that workflow/branch until a comparable successful observation; loss of connectivity cannot turn a known failure green. Each workflow/branch is decided by its newest decisive run: skipped runs decide nothing, `neutral` counts as passed, and a cancelled run followed by a newer run of the same workflow and branch was superseded (a cancelled newest run with no successor still needs attention). Exception for manual one-off audits (2026-10-25): a workflow listed in `MANUAL_COVERED_BY` (`cloudflare/monitor-journal.mjs`; today only `Verify existing live website (read only)`, covered by `Deploy verified website`) has `workflow_dispatch` as its only trigger, so nothing ever reruns it. Its cancelled run is shown `not-applicable` (green, never recorded as a success; symptom and evidence name the superseding run) once a newer successful run of the covering workflow on the same branch exists, from the scanned runs or the covering component's remembered healthy result. A failed manual audit is never superseded and stays red; a run recorded with any other trigger, a cancelled deploy, a cancelled scheduled run and any run with no newer successful covering run keep the rules above, and without GitHub data the component stays unavailable. The transition is listed under Recently resolved with its time. `scripts/monitor-noise.test.mjs` fails if a covered workflow gains another trigger or the covering workflow stops running the same live audits. The failure reporter (`Report workflow failure`) and performance logger are not build results. A workflow older than the 100 scanned runs keeps its last decisive result (remembered in the incident, or read once from the retained workflow log). Only `main` and branches with an open pull request are monitored: other branch components are retired once, green, with the merged/closed pull request (or missing pull request) recorded in the diagnostic and its history entry; their stored rows are never deleted, and opening a pull request brings the branch back. A `main` failure is never retired and stays red until a newer `main` run of that workflow succeeds. `Workflow: available results` appears only when GitHub data is unavailable or returned no runs.

### Overall status and Worker errors (2026-10-22)

`overall` keeps `color`, `label` and `reason` and adds `status` and `notes`. `status` is `healthy` (green), `failure` (red), `attention` (amber: every non-green required check is a confirmed *recent* problem in the `warning` state) or `unverified` (amber: a required check could not be verified). Older clients read only `color`.

`Worker execution errors` is rate- and recency-aware (`workerErrorCheck`). It compares the rolling 24-hour Cloudflare reading with the stored half-hour interval readings (window `[slot−30m, slot)`):

- **error (red)** when errors occurred in the newest measured half-hour, when some errors are not accounted for by any measured half-hour (for example the minutes since the last scheduled collection, or an unmeasured window — so they may be current), when the 24-hour error rate is at least 1% (`WORKER_ERROR_RATE_FAILURE`), or when the request count is unavailable;
- **warning (amber)** when every error is in an earlier measured half-hour and none since;
- **healthy** with zero errors; **unavailable** without a current reading (a previous confirmed failure stays red, as before).

The check keeps the original sentence and raw counts in its symptom and adds `errorCount`, `requestCount`, `errorRate`, `lastErrorWindow`, `brief` (`1 error in 24h`) and `lastAt` (end of the last half-hour with errors) for faces that format time locally. A warning still records its first occurrence; each colour change is a diagnostics history entry. Example (production, 2026-10-22 02:45 UTC): 1 error in 23,674 requests in the 00:00–00:30 UTC window and four later windows without errors → amber `ATTENTION · Worker execution errors · 1 error in 24h · last 8:30 PM` instead of a red failure for 24 hours.

### Widget freshness and synchronization devices (owner decisions, 2026-10-22)

- **Widget staleness: 35 minutes.** Both Android widgets draw a healthy reading amber (`HEALTHY AT LAST CHECK`) once it is more than 35 minutes old (`OwnerWidgetProvider.STALE_AFTER_MILLIS`, used by `statusColor` and `WidgetRows.status`). Background refresh is requested about every 30 minutes, so a normally refreshed widget stays green and a missed refresh shows. A red failure stays red at any age, and readings over one hour old are still hidden (`current()`). The web dashboard, which polls every minute while visible, keeps its two-minute stale rule (`owner-monitor.tsx`). The threshold is client-side only; the server sends no freshness setting to the widgets.
- **Active devices: 7 days.** `Widget synchronization` (`widgetSyncCheck`) counts only installations that reported within `DEVICE_ACTIVE_MS` (7 days). It is healthy when there is at least one active device and every active device reported within the owner's device threshold (`deviceFreshMs`, default 65 minutes); otherwise it stays amber/unverified, including when no device has reported for 7 days (silence is never healthy). Older installations are listed in the symptom as `inactive since <date>` and in `inactiveDevices` (`id`, `lastReportAt`) as information, not attention; a retired phone therefore no longer keeps the check amber. A device counts again as soon as it reports. Device rows and their history are never deleted.
- The 1% 24-hour Worker error-rate failure threshold is unchanged (owner accepted).

### Multiplayer round-trip probe (owner-approved 2026-10-22)

`cloudflare/multiplayer-probe.mjs` replaces the former "Storage was checked; no synthetic player session was created" coverage limit with a real measurement.

- **When and how often:** once per committed half-hour slot, from `collectInterval` after the interval is saved and before the dashboard snapshot is refreshed. A committed slot is never collected again (the slot lease and outcome guard), so the probe cannot run concurrently with itself; the room code is also unique per slot, and a run that finds this slot's room already present (or loses the insert race) reports `skipped` and leaves it alone. Only the deployed Worker (`ASSETS` bound) probes by default; tests and tools pass `multiplayerProbe` explicitly.
- **Round trip, through the real server room path** (`cloud.server.ts` / `room-store.server.ts`, the same functions the client server functions call): sweep leftovers → `openRoom` (DM seat, one player character) → `joinRoom` as a guest seat → authorization (an unseated token cannot read; an outside join is refused) → `submitCommands` one guest→DM chat message, then the same batch again (must stay at revision 3: idempotent) → `pollRoom` as the DM from revision 2 (must return revision 3 with the message) and from revision 3 (must answer `unchanged`) → a write from stale revision 2 must be rejected → `deleteRoom` with revision 3 and confirm the room is gone.
- **Footprint and isolation:** one `campaign_rooms` row, `MONITOR-PROBE-<slot>` with `monitorProbe: true`, for the duration of one run (typically well under a second; zero rows at rest). No account, `library_members`, image, resource, roll, encounter, push or policy rows are created (seats have no `userId`, the table has no media). Real codes never contain `-` (open: 8 letters/digits; Test mode `T`+7 hex; recovery 10 hex), so the namespace cannot collide. `probe-namespace.mjs` (`notProbeRoom()`) excludes it from the campaigns count in server health (`monitoring.mjs`, which feeds the Field monitor tiles, intervals and daily reports), the owner overview (`site-owner.mjs`) and game analytics/gold totals (`game-analytics.mjs`). Other campaign listings, moderation and search join through `library_members`, which the probe never writes. `previewRoom`/`joinRoom` answer "No table uses that code." for a probe room to everyone except the probe itself; the probe's access is a second, server-only argument that client server functions (single `data` argument) cannot supply. A known minor footprint: the sampled `lootsplit.sync-timing` console line (1% of reads, IDs omitted) can include probe reads.
- **Bounds and cleanup:** the whole run is limited to 10 s (`PROBE_TIMEOUT_MS`) plus up to 2 s grace for a late step to settle. On failure or timeout the slot's room is deleted directly; a room left by an interrupted run (Worker killed) is removed at the start of the next run (only codes from earlier slots). The probe never throws into collection.
- **Result and history:** each run is a `multiplayer` log entry (`multiplayer:<slot>`, built-in log "Multiplayer round-trip probe", included in daily reports with explicit gaps) with outcome, per-step timings, failed step, error code and cleanup result. Raw errors are not stored: unexpected exceptions read "the room service returned an unexpected error". `Multiplayer` diagnostic (required): **healthy** when the newest probe passed within 65 minutes (`PROBE_FRESH_MS`); **error** (red, `MULTIPLAYER_PROBE_FAILED` / `MULTIPLAYER_PROBE_TIMEOUT`, `brief: round trip failed`) when the newest probe failed — it stays red until a newer probe passes; **unavailable** (amber) before the first probe or when the last pass is older than 65 minutes. After deployment the check is amber until the first half-hour collection has probed.

### Cloudflare plan usage (owner request, 2026-10-22)

`cloudflare/cloudflare-usage.mjs` compares Cloudflare usage with the allowance included in the **Workers Paid** plan.

- **Allowances** live in one constant, `CLOUDFLARE_PAID_ALLOWANCES`, with source links and `verifiedOn` (2026-10-22): Workers 10,000,000 requests and 30,000,000 CPU ms per month ([Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)); D1 25,000,000,000 rows read and 50,000,000 rows written per month and 5 GB storage ([D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)). 5 GB is taken as 5×10⁹ bytes (the conservative reading). Re-check the pages before changing a value.
- **Daily and weekly figures.** Cloudflare includes usage per month, so: *today* (UTC day so far) is compared with the **daily share** = monthly allowance ÷ days in the current billing cycle (a cycle's daily shares add up to exactly its allowance); *7 days* (today and the six preceding UTC days) with the **weekly share** = 7 daily shares; the **billing cycle so far** with the full monthly allowance, alongside the share of the cycle already elapsed (`windows.month.elapsedPercent`) as the pace to compare against. Storage is a level, not a flow: the current total is compared with the 5 GB included.
- **Billing cycle (owner-supplied 2026-10-22).** Cloudflare resets included usage on the subscription renewal day, which the Analytics token cannot read, so it is configured: `CLOUDFLARE_BILLING_RENEWAL_DAY = 11` (next renewal 2026-11-11), overridable with the Worker var `OWNER_MONITOR_CLOUDFLARE_BILLING_DAY` (a whole number 1–31; anything else falls back to 11). A cycle runs from the renewal day at 00:00 UTC up to the next one (11th through the 10th), crossing month and year boundaries; in a month without that day (e.g. 31 in February) the renewal clamps to the month's last day. The window keeps the `windows.month` key for compatibility and adds `basis: "billing-cycle"`, `renewalDay`, `resetsAt` (next renewal) and `label` (`Cycle since Oct 11`). Readings stored before this change have no `basis`/`label` and still display as the calendar month.
- **Scope:** account-wide (no script filter), because the allowance is account-wide. Worker requests here can therefore differ from the `lootsplit`-only 24-hour traffic tile.
- **Collection:** hourly from the minute dispatcher (`collectUsage`, deployed Worker only; tests pass `cloudflareUsage` explicitly), with the existing `OWNER_MONITOR_CLOUDFLARE_ACCOUNT_ID` and Account Analytics Read token. Four GraphQL requests per hour, each failing independently: `workersInvocationsAdaptive` `sum.requests` and `sum.cpuTimeUs` (µs → ms) for the three windows (aliased), `d1AnalyticsAdaptiveGroups` `sum.rowsRead/rowsWritten`, and `d1StorageAdaptiveGroups` `max.databaseSizeBytes` (each database's newest day, summed). The entry id `usage:<UTC hour>` is claimed by the stored entry, so later minute ticks do not repeat the requests; a failed hour is retried the next hour.
- **Gaps, never zero:** a failed dataset leaves its metric `state: "unavailable"` with `errorCode` and null values; no storage rows is `NO_STORAGE_READING`; a not-connected or failed hour is stored with a `coverageGap`; the snapshot reports `NOT_COLLECTED` before the first reading and `STALE_READING` (no numbers) when the newest reading is over two hours old. A valid empty sum (no requests/rows in a window) is zero, as for traffic.
- **Where it shows:** `snapshot.usage` in `GET /api/account/owner/monitor` (also `?view=widget`), read from the log on every serve; website Field monitor → **Cloudflare plan usage** (today, 7 days and the billing cycle, e.g. `Cycle since Oct 11`, with value and share per metric); the main Android widget's scrolling rows (`Cloudflare plan usage` heading with reading time, then e.g. `Worker requests today 12,345` / `3.8% of daily share · 7d 80,000 (3.5% of weekly share) · Cycle since Oct 11 300,000 (3.0% of 10M)`; the heading row reads e.g. `37% of billing cycle elapsed · cycle since Oct 11`); daily reports (`cloudflareUsage`: readings, available readings, newest available reading and per-metric lines, plus coverage of the `cloudflare-usage` built-in log). Billing-cycle use at or above 80% of an allowance (`USAGE_ATTENTION_PERCENT`) is amber on the widget and the website and adds a report recommendation; it never makes overall status red, because overage is billed, not an outage. Usage does not add a diagnostic component.

### Field monitor widget data (owner-approved redesign, 2026-10-25)

The redesigned Android widgets (severity chips, Recently resolved, charts, CI pips, players and live rooms) read four additions that only the widget view (`?view=widget`) sends. The dashboard's full snapshot and history are unchanged. **None of them calls GitHub or Cloudflare:** they are read from rows the minute cron already writes, in `monitorWidgetData` (`monitor-journal.mjs`), before the request's final owner authorization re-check, so a revocation during the reads still fails closed. #264's request budget is untouched. Each part fails on its own into `{state: "unavailable", errorCode: "READ_FAILED"}`.

- **`series`** (`monitorSeries`): `halfHour` = requests and errors for the last 48 half-hour windows (`end` is the newest window end; `measured` of `expected`), and `daily` = the last 7 local calendar days in the report time zone, oldest first (`requests`, `errors`, `measured`, `expected`, `active24hMax`). Values come from each stored interval's `requests`/`errors` metrics, or its recovered provider history (`historicalTraffic`) when the slot was recovered. A missed, failed, partial-without-traffic or absent slot is `null`, never 0, and is left out of the day's sums, so a partial day states `measured: 19, expected: 22` instead of reading as a quiet day. The newest slot is treated as "not yet collected" (the series ends one slot earlier) only during the first 10 minutes after its boundary. One indexed range read of at most 336 interval rows (metric values extracted in SQL).
- **`recentlyResolved`** (`recentlyResolved`, owner decision 2): components that went from a problem back to green in the last 24 hours, newest first, at most 5 (`items`), with `total` (every resolved component found) and `complete` (false when the bounded scan of 400 diagnostics transitions, or 30 look-ups of problems that began before the window, was reached). Built from the `diagnostics` log, which has one entry per colour change. A component whose newest entry or current diagnostic is not green is still a problem and is not listed (a re-failure removes the item). Each item: `component`, `severity` (of the problem: `critical`, `warning` or `info`), `startedAt` (the problem's `firstOccurredAt`, kept even when it began before the window), `resolvedAt` (`recoveredAt`), `durationMs`, `resolution` (`recovered`, or `retired` for a finished branch), `brief`, `symptom`, `impact` and up to three `history` entries (time, colour, state, symptom).
- **`development.data.mainRuns`** (`mainRuns`, `owner-monitor.mjs`): the last 20 completed runs on `main` (scheduled housekeeping excluded) as `name`, `conclusion`, `at`, `deployment`, without URLs (about 1.5 kB). Running runs stay in `active`. Present only when the GitHub reading is ready.
- **`rooms`** (`liveRooms`, owner decision 4): `live` = shared rooms whose stored revision changed in the last 5 minutes (`LIVE_ROOM_MS`), i.e. a command, seat or other stored change; polling alone is not activity. The minute cron's `trackRoomActivity` reads every non-probe room's row id and revision (one bounded read, no bodies) into `owner_monitor_room_activity` (migration 0023) and writes only rooms whose revision changed; no room code or content is copied. Row 0 is the tracker's run record. The count is an explicit gap (`live: null`) with `NOT_COLLECTED` before the first run, `WARMING_UP` during the first 5 minutes (rooms seen on the first run have no change time, so idle rooms are never counted), and `STALE_READING` when the last run is over 3 minutes old. A database VACUUM that renumbers room row ids could count a room as live once; nothing else depends on it. It is current state, not a log, so it is not a registered source.
- **`diagnostics[].severity`** (`widgetSeverity`, `monitor-model.mjs`): `critical` for a confirmed failure (red), `info` for a coverage limit or optional check, otherwise `warning` (amber, including a required check that cannot be verified, owner decision 1); `null` when green. Cloudflare plan usage at 80% or more is not a diagnostic and never raises a severity or the warning count (owner decision 6: gauge only).

The widget payload stays well under the Android client's 256 KiB limit (`scripts/monitor-widget-data.test.mjs` asserts under 64 kB with 393 incident rows, the production size). Older widgets ignore the additions; newer widgets treat a missing addition (an older server) as "needs a server update", never as none.

## Task timing and warnings

Each task has persistent ID, revision, objective, phase, progress, state, start, heartbeat, meaningful-progress time, completion, branch/commit/evidence, blocker and next action. Updates use optimistic revisions and unique event IDs. Recorded active/testing/deploying spans require sufficiently close telemetry; missing spans are separately unobserved. Declared pauses and blockers have separate durations. Total elapsed wall time survives refresh, restart and handoff and includes waiting; it is not measured human effort.

Default heartbeat/progress thresholds are 5/30 minutes. Missing telemetry is distinguished from possible stalled progress. Warnings identify the task, last progress and telemetry, exceeded threshold, blocker and next action. Declared expected completion accommodates long builds/tests without inventing progress. Paused/blocked tasks keep their declared reason. A disconnected source is not proof work stopped.

`scripts/recovery-step.mjs` publishes bounded start, 20-second heartbeat and terminal events from authorized main workflows when `LOOTSPLIT_MONITOR_TELEMETRY=true`. GitHub OIDC verification checks signature, expiry, issuer, audience, immutable repository/owner IDs, exact main ref and permitted workflow/event. It accepts the exact legacy subject and the immutable-ID subject used by repositories created after July 15, 2026, including only the authorized production-environment context for website release. Wrong IDs or unrelated environments remain rejected. The ingestion route can only update its own run/attempt task namespace and cannot read owner data. Publication failure does not alter test outcomes or deadlines; it becomes missing telemetry. On SIGINT/SIGTERM (GitHub cancellation) the runner publishes its terminal interrupted result immediately, while stopping the child. If a step still never reports (runner killed), the stored row is left as recorded, but at read time a workflow step whose GitHub run is `completed`, was re-run as a newer attempt, or — when the run is outside the scanned 100 runs — whose heartbeat is over six hours old and a newer workflow step on its branch has finished, is presented as `interrupted` (`storedState` keeps the stored state, `endedBy` the run and conclusion), is not chosen as the active task and raises no heartbeat/stall warning. Independently of GitHub data, a workflow step whose own declared deadline (`expectedUntil`, set from the `recovery-step.mjs` timeout that the runner enforces) passed more than 15 minutes ago (`STEP_DEADLINE_GRACE_MS`) with no heartbeat for as long is presented as `interrupted` (`endedBy.reason: deadline-passed`); GitHub evidence is used first when present. This covers runs that have already left the 100 scanned runs, which previously stayed `TESTING` with a counting timer until the six-hour rule applied. Without GitHub data a step with no passed deadline keeps its stored state and warning unchanged. PR code and untrusted refs cannot publish operational state.

For manual tooling, securely supply the current owner's Lootsplit session as `LOOTSPLIT_OWNER_TOKEN` in the process environment, then run `node scripts/development-status.mjs event.json`. Never commit, print, extract from somebody else's browser, or put this credential in a file, URL or command argument. The JSON contains `id`, `eventId`, `revision`, `title`, `objective`, `state`, `phase`, `progress` and optional blocker/next action/expectedUntil/links. Read the current revision from the dashboard/API before a handoff. The task form is available without command-line credential handling.

## Website and Android behavior

The dashboard keeps account identity beside Owner access, essential status and task timing above a bounded scrolling area. It provides searchable/filterable chronological history, incremental older pages (Load older entries), Export loaded entries (saves exactly the entries currently loaded, with the `next` cursor; load older pages first to include earlier history), daily reports, diagnostics, settings and task publishing. Colors pair with labels: green means required checks current/healthy; yellow means stale/disconnected/unverified; red means a confirmed failure, retained across later disconnection. Overall status explains its determining components. Expand diagnostics for first/latest occurrence, duration, error, impact and action. A recent failed scheduled interval overrides an older success; a confirmed Worker error count is distinct from a healthy analytics connection. Reduced-motion controls and system preferences suppress gentle warning pulses.

Both platforms reject older snapshot IDs; task revisions independently prevent an older task from replacing newer progress. ### Agent activity companion (owner-approved 2026-10-21)

**Agent activity** is the default preset for new 4×1 companions; every earlier preset and category stays selectable. Companions placed before this release without saved settings keep the Development default: a one-time, upgrade-only check (`CompanionSettings.preserveLegacyDefaults`, run on `MY_PACKAGE_REPLACED` and before the first render) writes Development for them; saved settings are never rewritten, and a fresh install saves nothing.

- **Source:** GitHub only, through `developmentActivity()` and the existing read-only `OWNER_MONITOR_GITHUB_TOKEN` (Actions + Pull requests read). Three requests per collection: `actions/runs?per_page=100`, open pulls, and `pulls?state=closed&sort=updated&direction=desc&per_page=20` (for `merged_at`). The development chat, local work and unpushed changes are not visible; the widget and dashboard label this as GitHub activity.
- **Events:** `development.data.events` (≤20, newest first) built by `activityEvents()`: `run-started` (active), `run-succeeded` (ok), `run-failed` (fail; failure/timed_out/startup_failure), `run-cancelled` and `run-attention` (attention; e.g. action_required), `pr-opened`, `pr-merged` (ok), `pr-closed` (attention, closed without merging). Each has `id, kind, state, text, pr, title, at, url`. A run is linked to a pull request when its `head_branch` equals an open (preferred) or most recently closed pull request's `head.ref` (never `main`). Scheduled and skipped runs are excluded from events. Up to five running workflows are always kept even when newer events would push them out. `activeActivity` counts running, non-scheduled workflows. Existing `runs`, `active`, `openPulls` and `latestDeployment` keep their fields; `runs` adds `attempt`, `openPulls` adds `headRef`, and `closedPulls` (number, headRef, closedAt, mergedAt) lets diagnostics retire finished branches.
- **Cache:** the provider cache is 55 seconds while `activeActivity > 0`, otherwise five minutes (also after a failure). Worst case about 66 collections (~200 GitHub requests) per hour per Worker isolate while active, 36 requests idle, well within GitHub's 5,000 authenticated requests per hour; the existing 60-second snapshot reuse in `monitorSnapshot` still applies.
- **Payload:** the events ride in the existing owner snapshot (`GET /api/account/owner/monitor`, owner-only authorization unchanged). The native projection keeps at most six events as `activity: {state, reason, active, checkedAt, events[]}`.
- **Face:** the glyph box shows the latest event's state (✓ ok, ! running/attention, ✕ failure; the same glyph rules and colours as the redesigned widgets). Line 1: `Merged #138 · Widget redesign · 2m`; line 2: the running workflow if it is not the latest event, otherwise the previous event (prefixed by its glyph), or `GitHub activity · checked 12:04`. A failed refresh keeps the dated reading and says so on line 2. Ages are computed at each render and are shown only while the one-minute cadence is re-rendering (a workflow is running and the reading is under 30 minutes old); otherwise the event's clock time is shown, so an idle face never shows an age that stopped advancing. Unavailable GitHub data is explicit — `GitHub activity unavailable · rate limited` / `access denied` / `timed out` / `GitHub error 502` / `no response`, `GitHub activity not connected`, or `… · not provided by server` for an older Worker — and is never shown as "no activity"; only a successful empty read shows `No recent GitHub activity`.
- **Tap:** the glyph and both lines open My account → Field monitor → Development & deployments (`#field-development`), which lists recent GitHub activity with links.
- **Refresh cadence:** while a non-scheduled workflow is running, an Agent activity companion is placed, the owner is connected and the reading is under 30 minutes old, `WidgetRefresh.scheduleActivity` arms an inexact **RTC (non-wakeup)** `AlarmManager` alarm about 60 seconds after each render. It never wakes the device; a tick that arrives while the screen is off only re-arms, so the next refresh happens when the phone is next awake. Each tick uses the normal background `WidgetRefresh.request` path (coalescing, eight-second deadline, account generation checks). The alarm is cancelled when nothing is running, no companion shows Agent activity, on sign-out/disconnect and when the last widget is removed; the persisted ~30-minute `OwnerWidgetJob` remains the background cadence otherwise. No push notifications or Firebase. Each widget refresh also upserts its device report (one log entry per collection interval).

Android RemoteViews do not offer portable continuous custom animation. Status changes render on supported refreshes, with equivalent static symbols/text; there is no battery-draining animation/network loop. Native `Chronometer` advances elapsed time without network calls. Its movement never proves recent progress or fresh data; the adjacent reading timestamp remains authoritative. Actual OEM launcher, large-font, Doze, offline/reboot and accessibility behavior requires device validation beyond emulator checks. Do not label synthetic fixtures or emulator screenshots as production-device observations.

## API, export and recovery

All `/api/account/owner/monitor/*` routes require the current active owner session, enforce request origin, return `no-store` and recheck authorization. Writes include live authorization in their commit predicates. `GET history`/`export` accept `source`, `q`, `since`, `until`, `limit` (max 100) and opaque `before`; follow `next` until null for full export. Ordering is observation time plus sequence, so late evidence remains chronological. `GET registry`, `task`, `reports` expose current private records; reports paginate by `before` day. `POST registry` registers future/external logs, `registry/retire` and `registry/reinstate` retire or reinstate a custom log (see above), `entry` accepts stable ID/actual observation time/summary/evidence, `task` publishes an idempotent revision, `settings` changes reporting thresholds, `device` reports delivery, and `report` regenerates a completed day. Evidence URLs allow only credential-free Lootsplit/GitHub/Cloudflare links. Technical failures are sanitized; never submit credentials or unnecessary personal information as log text.

There is **no automatic history deletion**: logs, intervals and reports are kept. The one owner-approved retention rule (2026-10-21) applies to `owner_monitor_snapshots`, a provider-read cache of which only the newest row is ever served; the newest 48 rows are kept and older cache rows are deleted. For archives, export every history page: in the dashboard choose Load older entries until none remain, then Export loaded entries; through the API, follow `next` until null (the API's `retention` text says "Export all pages" for that reason). Export reports too; preserve original evidence before any other separately reviewed retention change. Provider retention is independent.

**Queued refresh cap (2026-10-22).** Late observations queue an already generated report in `owner_monitor_report_refresh`. A failing refresh backs off 1, 2, 4, 8, 16 minutes and stops after `REPORT_MAX_ATTEMPTS` (6) failures counted since that report was last stored (the same cap as the first-generation placeholder path); an error with a 4xx status stops it at once. Stopping deletes nothing: the queue row stays (skipped while a `report-refresh-stopped:<reportId>:<generated_at>` entry exists), the stored report keeps its `generated_at` and gains `refreshStopped { at, attempts, error }` plus a first coverage gap saying it is out of date, and a failed `reports` entry with the error keeps **Daily reporting** red (website and widget diagnostics). **Retry refresh** on that report (`POST report` with `{ day, timezone }` of a stored report) or any successful generation replaces the report, clears the queue row and turns Daily reporting green; the next failing refresh starts a fresh count.

Report size is bounded below D1's 2 MB row limit (owner-approved 2026-10-21). Counts, coverage, gaps, recommendations and unresolved diagnostics are never reduced. When a report would exceed the budget, its long lists (evidence, correlations, builds, performance, incidents, trends, development task views) keep failures, errors and regressions first and then the most recent entries; the report's `summarized` field and summary state exactly how many entries were shown, and every entry remains in paginated History. A report that still cannot fit fails explicitly. Failed generation retries with backoff (1, 2, 4 … 32 minutes); after six failed attempts an explicitly failed placeholder (no measurements) is stored so later days continue, Daily reporting stays red until a real report for that day succeeds, and Generate previous day or a queued refresh replaces it. Failing queued regenerations are deferred with the same backoff instead of retrying every minute. Each failure entry records the thrown message (`error`). Monitor D1 size and report failures as history grows. D1 bills rows read: report pages follow the `(observed_at, sequence)` chronology index with a keyset cursor (about 200 rows per page), and the current-task reads on every dashboard serve use the partial indexes from migration 0020; a test fails if any monitor task or log read scans its table.

Recovery: reconcile live source, scheduled executions, recent slots and leases first; verify `* * * * *` Cron readback after deployment (propagation may take up to 15 minutes). Restore D1/integration connectivity, allow bounded catch-up, inspect missing/recovered entries and report coverage, then use Generate previous day if needed. Never manually invent healthy historical measurements or delete failed entries. GitHub public collection requires `OWNER_MONITOR_GITHUB=true`; investigate provider rate limits/HTTP codes without assuming credential expiry. A403 with exhausted-rate-limit or retry headers is identified as a request limit; other 403 responses have an unconfirmed cause. If anonymous GitHub API quota is insufficient, configure the optional server-only `OWNER_MONITOR_GITHUB_TOKEN` through the existing authorized secret process, with only read access to this repository's Actions and pull requests. Never copy a connector/deployment credential. Performance history uses the public raw files and reports its own sanitized collection error independently. Restricted provider/signing-key requests use Workers-supported manual redirect handling and reject non-success responses; never use its unsupported `error` redirect mode. Cloudflare traffic uses the existing server-only account ID and Account Analytics Read token; verify scope/expiry in the provider dashboard and replace only through the authorized secret workflow. Do not expose or reuse deployment credentials. The standby can serve available shared snapshots but is not a second scheduler.

This covers Android versions that deliver the second broadcast after the first goAsync result finishes. It never delays a retry after failure or changes the background schedule.
