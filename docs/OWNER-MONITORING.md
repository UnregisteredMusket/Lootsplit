# Owner monitoring, development status and widgets

Lootsplit's owner dashboard, bundled Android account screen, main Field monitor and independent 4×1 companion read the same private backend. Campaign DM, player, moderator and administrator roles do not grant owner monitoring access. Existing server monitoring, owner controls, gameplay, saves and permissions remain available.

## Permanent log and development rules

**Every future log explicitly requested or designated for Lootsplit must automatically become part of the daily report.**

Register each log before its first entry. In-code producers add a definition to `BUILTIN_LOGS` in `cloudflare/monitor-journal.mjs`, emit through its journal interface, and test both inclusion and missing-source coverage. No producer may maintain a separate invisible report history. Logs introduced outside this repository use **My account → Field monitor → Log registry & settings → Register an external or future log**, followed by **Record an external log entry or coverage check** or the authenticated API below. A registration is not proof that a source supplied data. Missing registered sources remain explicit coverage gaps. Original logs remain authoritative evidence; this registry cross-references them.

Every development session publishes an explicit task start, meaningful progress, phase changes, expected long operations, pauses, blockers, handoffs and completion. Use the owner task form or `scripts/development-status.mjs`. Never infer activity from an open chat, old commit, queued PR or somebody's presumed availability. A handoff continues the existing task ID and revision. A new update receives a new ID. Store real evidence links and a useful next action. If publishing is unavailable, state the telemetry gap and publish the actual current state when restored; do not invent past heartbeats.

## Collection and reports

Migration `0016_owner_monitoring.sql` adds only private operational tables. Cloudflare's minute Cron dispatcher claims each UTC half-hour slot with a database lease; measurement collection runs once per slot, independently of phones, browsers and app processes. Entries retain scheduled time, actual collection time, outcome, attempt history, source freshness, measurement window, previous/current values, absolute changes and meaningful percentages. Retries use persistent IDs; a failed slot retries with backoff (1, 2, 4 … 32 minutes, at most six attempts) so a provider outage cannot multiply provider calls every minute. Failures and missed slots remain in history even after recovery. Expected intervals in a report count only slots after monitoring was installed; an unmonitored part of the first day is stated as a gap, not counted as missed. The interval whose window ends at local midnight belongs to the day it measured.

Instantaneous counts, rolling 5-minute/24-hour observations, cumulative current-campaign counters and exact preceding half-hour traffic totals are distinct. Missing readings are null/unavailable. Zero baselines have no percentage; decreased cumulative counters identify a reset/restoration/deletion rather than a negative rate. Changes compare the preceding available observation and retain its scheduled time. Counter totals can decrease when current campaigns change; they are not lifetime business totals. GitHub and 24-hour provider reads may be cached five minutes. Adaptive provider metrics retain the provider's scope; they are not an exact count of people online.

The dispatcher records older missed slots in bounded batches and attempts historical traffic recovery separately. Recovery never reconstructs unobserved storage, authentication, device or development state. A conservative 89-day historical traffic horizon avoids treating data beyond the provider's documented three-month retention as zero. Unrecoverable intervals remain gaps. Current collection continues after the backlog drains. An expired lease can be retried; an interrupted older observation becomes explicitly missed. Cron execution failure remains visible in Cloudflare; collection/report failures also receive sanitized journal entries when D1 is available. No database outage can be logged into that same database until storage recovers: inspect Cloudflare execution evidence and resulting missing slots.

Daily reports default to **00:10 America/New_York**, for the preceding calendar day. The owner can change the IANA timezone, local report time and warning thresholds in the dashboard. DST days retain their real 23/25-hour coverage. Half-hour traffic windows ending after the day's start and through its end belong to that report. Reports include every registered source, trends, incidents/recoveries, build/test/audit/deployment metadata, task states as of day end, performance history, evidence, missing coverage and recommended actions. Nearby events are described as correlation, never proof of cause. Late entries queue regeneration of already-created affected reports. Missed reports catch up one day per dispatcher invocation. A failed regeneration retains the previous report, but the daily-report component stays red until the same calendar report succeeds. Recovered traffic is displayed separately from the original unavailable measurement, with its actual recovery time and comparison window.

Existing performance capture remains on the `performance-history` branch. Its regressions, verified resolutions and capture cursor feed the daily report. **Inclusive ≥15% comparable slowdowns must still be investigated and documented under `docs/PERFORMANCE.md`.** Compare equivalent workloads and environments. Faster runs alone never reset a trend; retain the original history and use `performance:resolve` only after a diagnosed fix and successful comparable verification. Monitoring does not change these rules or label unavailable capture as healthy.

## Registered sources and coverage limits

| Source | Evidence and limitations |
| --- | --- |
| Monitoring | Durable half-hour observations, failures, missed slots and historical recovery |
| Performance | Existing regression/resolution files plus recorder cursor; bulk import avoids per-event query overhead |
| Workflows / recovery | Latest 100 GitHub runs, canonical run links and outcomes; reaching the bound is an explicit coverage gap |
| Development | Explicit task events and telemetry; no inference from chat or commit age |
| Diagnostics | Component status transitions, retained failures and recovery observations |
| Devices | Actual reports from each installation, version and previously delivered snapshot; silence does not prove failure |
| Reports | Generated reports and generation failures |
| Administration | Sanitized action summaries from existing member/site audits; 500-record source bounds are disclosed |
| Application issues | Aggregate retained report counts; private issue contents remain in their existing staff interface |
| Runtime logs | Registered Cloudflare invocation/application timing source; raw retained logs require an external export feed and remain a coverage gap until supplied. Aggregate traffic does not substitute for raw logs |

The storage/assets checks are real observations. Multiplayer's full player-to-room round trip is explicitly unverified by scheduled collection; the collector never creates fake production campaigns. Use existing connection indicators and linked preservation audits. A failed candidate workflow does not mean the deployed app failed. Workflow failures remain associated with that workflow/branch until a comparable successful observation; loss of connectivity cannot turn a known failure green.

## Task timing and warnings

Each task has persistent ID, revision, objective, phase, progress, state, start, heartbeat, meaningful-progress time, completion, branch/commit/evidence, blocker and next action. Updates use optimistic revisions and unique event IDs. Recorded active/testing/deploying spans require sufficiently close telemetry; missing spans are separately unobserved. Declared pauses and blockers have separate durations. Total elapsed wall time survives refresh, restart and handoff and includes waiting; it is not measured human effort.

Default heartbeat/progress thresholds are 5/30 minutes. Missing telemetry is distinguished from possible stalled progress. Warnings identify the task, last progress and telemetry, exceeded threshold, blocker and next action. Declared expected completion accommodates long builds/tests without inventing progress. Paused/blocked tasks keep their declared reason. A disconnected source is not proof work stopped.

`scripts/recovery-step.mjs` publishes bounded start, 20-second heartbeat and terminal events from authorized main workflows when `LOOTSPLIT_MONITOR_TELEMETRY=true`. GitHub OIDC verification checks signature, expiry, issuer, audience, immutable repository/owner IDs, exact main ref and permitted workflow/event. It accepts the exact legacy subject and the immutable-ID subject used by repositories created after July15,2026, including only the authorized production-environment context for website release. Wrong IDs or unrelated environments remain rejected. The ingestion route can only update its own run/attempt task namespace and cannot read owner data. Publication failure does not alter test outcomes or deadlines; it becomes missing telemetry. PR code and untrusted refs cannot publish operational state.

For manual tooling, securely supply the current owner's Lootsplit session as `LOOTSPLIT_OWNER_TOKEN` in the process environment, then run `node scripts/development-status.mjs event.json`. Never commit, print, extract from somebody else's browser, or put this credential in a file, URL or command argument. The JSON contains `id`, `eventId`, `revision`, `title`, `objective`, `state`, `phase`, `progress` and optional blocker/next action/expectedUntil/links. Read the current revision from the dashboard/API before a handoff. The task form is available without command-line credential handling.

## Website and Android behavior

The dashboard keeps account identity beside Owner access, essential status and task timing above a bounded scrolling area. It provides searchable/filterable chronological history, incremental older pages, export of loaded entries, daily reports, diagnostics, settings and task publishing. Colors pair with labels: green means required checks current/healthy; yellow means stale/disconnected/unverified; red means a confirmed failure, retained across later disconnection. Overall status explains its determining components. Expand diagnostics for first/latest occurrence, duration, error, impact and action. A recent failed scheduled interval overrides an older success; a confirmed Worker error count is distinct from a healthy analytics connection. Reduced-motion controls and system preferences suppress gentle warning pulses.

Both platforms reject older snapshot IDs; task revisions independently prevent an older task from replacing newer progress. Native app receipt updates all widget instances from the same encrypted local snapshot. A widget report identifies its actual last delivery; the dashboard never claims simultaneous Android freshness. Cached timestamps remain visible. Logout/account switches and authorization rejection clear sensitive cached displays; remote revocation is learned on the next connected check, with the existing one-hour native display limit retained. Offline launchers cannot learn a remote revocation immediately.

Android manual Refresh retains the 1.8.1 direct foreground-broadcast path, an eight-second bounded request, tap coalescing, generation/account isolation and clear timeout feedback. It does not wait for My account. Valid stored authorization is sufficient. Expired or revoked authorization clears access and shows a working Sign in route. Periodic JobScheduler work is persisted across restart, requires connectivity and requests 30-minute updates; Android/OEM battery management may defer it. Backend logging continues regardless. An app reconnect/owner refresh distributes the new local snapshot to every installed instance.

The main widget uses supported collection controls: `RemoteCollectionItems` on API31+, and a protected `RemoteViewsService` on API24–30. Scroll its rows for analytics, logs, diagnostics and reports; tap for full details. Its launcher or My account appearance controls offer existing terminal styling, light, dark and system choices.

Add the separate **Lootsplit 4×1 companion** from My account or the launcher's Widgets menu. Android1.9.1 allows placement before connecting owner access, uses the existing Development preset by default and keeps Settings available after placement. Upgrades reannounce both providers without removing existing instances. My account → Refresh widget list reports Android discovery and requests updated metadata; private readings still require the same owner authorization. Some third-party launchers (for example Lawnchair) can keep an old widget list after an update; if the 4×1 companion is missing from the launcher's Widgets menu, add it from My account → Home-screen Field monitor → **Add 4×1 companion**. Configure each instance independently: Development, Server Health, Analytics or Quick Actions preset; two summaries in top-to-bottom order; two toolbar actions; appearance. Categories include service health, account/game analytics, traffic, task, timer, log explanation, warning and daily report. Each summary links to full detail. Actions include Refresh, logs, daily report, task, diagnostics, website, owner account and settings; the configuration screen exposes additional actions. Two 44×48dp toolbar targets fit the intended four-column/one-row layout with a 250×56dp legacy minimum; launcher grids and font scaling can affect actual dimensions.

Android RemoteViews do not offer portable continuous custom animation. Status changes render on supported refreshes, with equivalent static symbols/text; there is no battery-draining animation/network loop. Native `Chronometer` advances elapsed time without network calls. Its movement never proves recent progress or fresh data; the adjacent reading timestamp remains authoritative. Actual OEM launcher, large-font, Doze, offline/reboot and accessibility behavior requires device validation beyond emulator checks. Do not label synthetic fixtures or emulator screenshots as production-device observations.

## API, export and recovery

All `/api/account/owner/monitor/*` routes require the current active owner session, enforce request origin, return `no-store` and recheck authorization. Writes include live authorization in their commit predicates. `GET history`/`export` accept `source`, `q`, `since`, `until`, `limit` (max100) and opaque `before`; follow `next` until null for full export. Ordering is observation time plus sequence, so late evidence remains chronological. `GET registry`, `task`, `reports` expose current private records; reports paginate by `before` day. `POST registry` registers future/external logs, `entry` accepts stable ID/actual observation time/summary/evidence, `task` publishes an idempotent revision, `settings` changes reporting thresholds, `device` reports delivery, and `report` regenerates a completed day. Evidence URLs allow only credential-free Lootsplit/GitHub/Cloudflare links. Technical failures are sanitized; never submit credentials or unnecessary personal information as log text.

There is **no automatic history deletion**: logs, intervals and reports are kept. The one owner-approved retention rule (2026-10-21) applies to `owner_monitor_snapshots`, a provider-read cache of which only the newest row is ever served; the newest 48 rows are kept and older cache rows are deleted. Export every history page and reports for archives; preserve original evidence before any other separately reviewed retention change. Provider retention is independent.

Report size is bounded below D1's 2 MB row limit (owner-approved 2026-10-21). Counts, coverage, gaps, recommendations and unresolved diagnostics are never reduced. When a report would exceed the budget, its long lists (evidence, correlations, builds, performance, incidents, trends) keep failures, errors and regressions first and then the most recent entries; the report's `summarized` field and summary state exactly how many entries were shown, and every entry remains in paginated History. A report that still cannot fit fails explicitly. Failed generation retries with backoff (1, 2, 4 … 32 minutes); after six failed attempts an explicitly failed placeholder (no measurements) is stored so later days continue, Daily reporting stays red until a real report for that day succeeds, and Generate previous day or a queued refresh replaces it. Failing queued regenerations are deferred with the same backoff instead of retrying every minute. Monitor D1 size and report failures as history grows.

Recovery: reconcile live source, scheduled executions, recent slots and leases first; verify `* * * * *` Cron readback after deployment (propagation may take up to15 minutes). Restore D1/integration connectivity, allow bounded catch-up, inspect missing/recovered entries and report coverage, then use Generate previous day if needed. Never manually invent healthy historical measurements or delete failed entries. GitHub public collection requires `OWNER_MONITOR_GITHUB=true`; investigate provider rate limits/HTTP codes without assuming credential expiry. A403 with exhausted-rate-limit or retry headers is identified as a request limit; other403 responses have an unconfirmed cause. If anonymous GitHub API quota is insufficient, configure the optional server-only `OWNER_MONITOR_GITHUB_TOKEN` through the existing authorized secret process, with only read access to this repository's Actions and pull requests. Never copy a connector/deployment credential. Performance history uses the public raw files and reports its own sanitized collection error independently. Restricted provider/signing-key requests use Workers-supported manual redirect handling and reject non-success responses; never use its unsupported `error` redirect mode. Cloudflare traffic uses the existing server-only account ID and Account Analytics Read token; verify scope/expiry in the provider dashboard and replace only through the authorized secret workflow. Do not expose or reuse deployment credentials. The standby can serve available shared snapshots but is not a second scheduler.

References: [Cloudflare Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/), [Workers metrics retention](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/), [Android widget collections](https://developer.android.com/develop/ui/views/appwidgets/collections), [Android widget layouts](https://developer.android.com/develop/ui/views/appwidgets/layouts), [RemoteViews timers](https://developer.android.com/reference/android/widget/RemoteViews#setChronometer(int,long,java.lang.String,boolean)), [GitHub OIDC reference](https://docs.github.com/en/actions/reference/security/oidc).

Rapid manual taps share the active request or a successful result completed within the preceding two seconds for the same authorization generation. This covers Android versions that deliver the second broadcast after the first goAsync result finishes. It never delays a retry after failure or changes the background schedule.

### Private owner Field monitor

`/api/account/owner/monitor` reuses server health and canonical aggregate game analytics. Check active account, current owner role and unexpired session before and after bounded provider reads. Return only the authenticated account’s name/email and allowlisted aggregates/release metadata; no-store remains mandatory. The original owner/admin server monitor and owner controls remain intact. Provider snapshots are cached five minutes per database/isolate, with request coalescing and explicit unavailable/disconnected states. GitHub public activity is opt-in through `OWNER_MONITOR_GITHUB=true`; local development leaves it off. Optional Cloudflare traffic uses `OWNER_MONITOR_CLOUDFLARE_ACCOUNT_ID` plus server-only `OWNER_MONITOR_CLOUDFLARE_TOKEN` scoped to Account Analytics Read. Never reuse a deployment token in the client, claim local coding activity from GitHub, infer a serving version from workflow success, or turn missing readings into zero. The shared owner dashboard is included in the website and bundled Android account screen. Native providers retain separate encrypted account controls and independent refresh. Keep fixed HTTPS/no-redirect/no-store bounded transport; Android Keystore AES-GCM storage belongs under noBackupFilesDir. Never place tokens in RemoteViews, intents, URLs, logs or backups. Clear before account switches/sign-out and on auth rejection; generation/token checks must reject older results without clearing a newly connected account. Missing sources never become zero, every reading is dated, and OS-managed30minute updates are not a real-time guarantee. Manual taps use the foreground broadcast/goAsync path with an eight-second shared request deadline, not the deferred periodic JobScheduler queue. Release every pending broadcast on success/error/timeout; ignore late completions, coalesce rapid taps, and keep dated cached data only within the existing one-hour display limit. Transport failure must not erase the last reading; authentication rejection still clears access. Test the actual RemoteViews Refresh PendingIntent with no resumed activity, plus timeout and late-account isolation. Keep API24/API35 instrumentation, synthetic mobile-control browser checks and the native release dependency in android-widget.yml. Local Java networking may be unavailable even when Python/Node network access works: record that gap and use the native CI gate, never weaken it. Preserve the permanent certificate, increment code/version, and advance website release metadata only after independently inspecting the signed APK. Extend account/provider tests and the existing monitor browser/Worker audits, preserving original scenarios and full release gates. See the owner-monitor audit for credential availability and phone-widget scope.

### Permanent operational journal and development publishing

**Every future log explicitly requested or designated for Lootsplit must automatically become part of the daily report.** New code producers register in `BUILTIN_LOGS`; external logs register through the owner dashboard or authenticated registry/entry API. Tests must prove inclusion and explicit missing-data coverage. Read `docs/OWNER-MONITORING.md` before changes. Recover leases/missed slots and late-report queues rather than manufacturing past observations.

### Monitoring integration contracts

GitHub's default OIDC subject includes immutable owner/repository IDs for repositories created after July15,2026. Lootsplit verifies the exact authorized new or legacy subject alongside independent signed IDs, issuer/audience, main ref, workflow/event and run namespace. Keep positive/negative real-signature coverage when provider contracts change; never solve a telemetry failure by removing authorization checks. HTTP403 alone does not establish token expiry. Use sanitized status/rate-limit/timeout evidence, retain coverage gaps and never store raw provider headers/bodies or credentials. See `docs/OWNER-MONITORING.md` for server-only optional read-token setup and recovery.

Use `redirect: "manual"` and explicit non-success rejection for restricted monitoring/JWKS requests. Workers does not implement the browser's `error` redirect mode; it throws before sending. Keep `scripts/monitor-runtime.test.mjs`, which exercises the production modules and actual RSA verification in pinned workerd, alongside real SQLite and provider-boundary tests. Node-only fetch mocks cannot establish edge-runtime compatibility.
