# Lootsplit bug audit — October 2, 2026

Audited release: `a551e1024f7fd23530f18b63691a763cc2e4a07d` (PR #12). The release's application source was unchanged during this audit. Findings below were reproduced with disposable local browser storage or an isolated database. The live-site smoke check used guest-local data and made no production account/campaign writes. Fixes have not been deployed.

## Result

The existing regression suite still passes: **387 passed, 4 skipped**, zero failures. Type checking passes; lint has zero errors and 34 warnings. Fresh exploratory probes identified **six areas requiring fixes**, including a data-loss path and inconsistent enforcement of player-owned sheet protection. Passing existing tests did not cover these cases.

## Reproduction and evidence

### 1. Older editor: data loss and read-only inconsistency

A disposable character contained level 9, proficiency 4, temporary HP 7, inspiration, a condition, an initiative adjustment, trained Athletics and custom notes, alongside an older imported sheet whose Race field was blank. In Party → Funds & inventory, filling Race with `Human` and leaving the input saved automatically.

Persisted result: level 1, proficiency 2, temporary HP 0, inspiration false, empty conditions, zero initiative adjustment, untrained Athletics and empty custom notes. Race saved correctly. Attacks, spells, slots and resources have explicit preservation code, but the other fields do not.

A separate real room-handler probe set the player-owned read-only marker. The modern `character` command correctly rejected the DM's stat edit. The alternate `sheet` command accepted an HP change from 8 to 1 while the read-only marker remained true. This demonstrates inconsistent handling of the existing restriction; it does not establish that ordinary players can edit arbitrary characters or mint money.

Locations: `src/lib/quire/economy.ts` (`updateCharacterSheet`), `src/lib/quire/commands.ts` (`sheet` branch), `src/components/character-sheet.tsx` (`BlankFields`).

Immediate workaround: use the full **Edit sheet** form; avoid filling missing fields or re-importing through the older embedded sheet editor until corrected. Export a backup before legacy-sheet edits.

### 2. Older imports: partial conversion

Loaded an old-save character with `Fighter 9`, proficiency +4, STR 18, Athletics +8 and initiative +5. The full sheet retained `Fighter 9` as class text but showed level 1 and proficiency +2, defaulted Athletics training/extra, and omitted the additional initiative adjustment. Original source fields remained in the older saved sheet; the playable projection was wrong.

Location: `src/lib/characters/campaign-sheet.mjs` (`legacyCharacter`). This incomplete conversion also feeds the older import/edit paths. The account import path has separate conversion logic, so the finding should not be generalized to every import format.

### 3. Older local characters: display and dice disagree

For the same old-save fixture, the sheet detail returned STR 18. A local STR ability roll returned formula `1d20+0`; the correct formula for the displayed score is `1d20+4`. The local roll function reads the purse and holdings but does not read the legacy sheet stored in campaign metadata. The shared server roll path already supplies that legacy sheet.

Location: `src/lib/quire/character-roll-client.ts` (`campaignRollRequest`).

### 4. Guest campaign switch retains stale selection

Created two local campaigns in a signed-out browser, opened `/characters` in the first, and selected the second through the actual Campaigns menu's Open button. The campaign selector and storage moved to the second campaign. The editor continued displaying the first campaign's Drugis Falkson and showed `This character is not controlled by your campaign seat.` The second campaign contained its own valid playable character.

The account-request failure branch retains the old selected ID before considering the new campaign character; the editor also retains its previous detail when the new load fails. No cross-campaign write was demonstrated.

Location: `src/components/characters/workspace.tsx` (selection effect and editor load effect). Workaround: reopen the character from the new campaign's Party card.

### 5. Long inventory name prevents HP saves

Added a valid inventory item with a descriptive name longer than 120 characters. The inventory accepts that name. Opened its owner's full sheet, changed HP from 10 to 4, and clicked Save character. Save failed with an equipment-name validation error; persisted HP remained 10. This can block a player who cannot rename the offending item.

Locations: `src/lib/quire/validation.ts` (unbounded holding name), `src/lib/characters/model.mjs` (120-character equipment name), and full-sheet save validation. The correction must preserve existing item text rather than silently truncating it.

### 6. Local transfers lose item metadata

Transferred a custom weapon between two local characters. Before transfer it had weight 3, a custom ability note, an image and category Weapons. The recipient received the correct name, quantity and unit value, but notes became empty and weight/image/category were missing. The shared-command transfer copies the holding; the local/manual gift representation carries fewer fields.

Locations: `src/lib/quire/economy.ts` (`giveToPlayer`), `src/lib/quire/gift.ts`, and manual transfer application in `src/lib/quire/cloud.ts`. The executed reproduction covers the local transfer; the manual path's missing fields were identified by source inspection.

## Reusable probes and scope

New audit scripts reproduce the failures and return exit code 1 while the checked expectations fail. They are separate from the existing `npm test` count and are not yet added to CI:

- `scripts/bug-audit-edge-cases.mjs` — old-save projection/dice and guest campaign switching.
- `scripts/bug-audit-data-integrity.mjs` — legacy field editing and long-item-name HP save.
- `scripts/bug-audit-permission-transfers.mjs` — server permission consistency and local item metadata.

Run the first two against the existing local development server using Node/Playwright; set `CHROMIUM_EXECUTABLE_PATH` when required. Run the third with Node's `--experimental-strip-types`. The scripts use disposable fixtures and never target real user campaigns.

This is a targeted regression and exploratory audit, not exhaustive proof of every function. Native Android hardware behavior, every external PDF/export format, external Open5e availability and production load/soak testing were not covered in this pass. Existing app behavior and production data were not changed. Fix the destructive legacy save path and permission inconsistency first, then conversion/dice, followed by campaign selection, validation compatibility and transfer metadata; retain each reproduction as a regression gate.
